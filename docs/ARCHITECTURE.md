# argus — architecture proposal

> The model-agnostic extension (cloud providers, profiles, sandboxing, sessions,
> TUI) is proposed in [MODEL-AGNOSTIC.md](MODEL-AGNOSTIC.md).

A personal, headless coding-agent harness for a local Qwen model behind
`llama-server` (OpenAI-compatible, `127.0.0.1`). The harness is also a
measurement instrument: every run is logged to SQLite in enough detail to
answer "why did this run fail, and did config B do better than config A?".

## Goals (priority order)

1. **Minimal overhead.** Short system prompt, terse tool schemas, and a
   command that measures exactly how many tokens they cost.
2. **Constrained tool calls.** Tool calls that cannot be malformed, via
   llama-server grammars / JSON-schema.
3. **Structured logging.** Full reasoning, per-turn token counts, tool calls,
   timings and failure tags (`loop`, `overrun`, `malformed_call`, `token_cap`).
4. **Tools.** `read`, `edit` (search/replace, fuzzy), `bash` (smart
   truncation), `glob`, `grep` — identical behaviour locally and over SSH.
5. **Safety net.** Git checkpoint before each mutating call; post-tool
   filesystem checks.
6. **Project context.** `AGENTS.md` and `SKILL.md` loading; skill invocations
   logged.
7. **Compaction** using a separate small model.
8. **CLI**: run a task, replay a task suite, A/B two configs.

Non-goals: interactive TUI, multi-agent orchestration, remote/hosted APIs,
MCP. Only one runtime dependency (`httpx`); everything else is stdlib
(`sqlite3`, `tomllib`, `difflib`, `argparse`, `http.server`).

## Overview

```
                 ┌──────────── argus CLI (run / suite / ab / overhead / show) ───────────┐
                 │                                                                       │
                 ▼                                                                       ▼
        ┌─────────────────┐   request/parse   ┌──────────────┐   HTTP+SSE    ┌──────────────────┐
        │   Agent loop    │ ◄───────────────► │  Protocol    │ ◄───────────► │ llama-server     │
        │  (agent.py)     │                   │ native/json/ │               │ (or MockServer)  │
        │                 │                   │ grammar      │               └──────────────────┘
        │  detectors ─────┼─ failure tags     └──────────────┘
        │  compactor ─────┼──────────────────────────────────────────────►  small-model server
        │                 │
        │  tools ─────────┼──► Executor (local | ssh) ──► workspace
        │  fsstate ───────┼──► shadow git (checkpoints, change detection)
        │  store ─────────┼──► SQLite (runs, turns, messages, tool_calls, failures, …)
        └─────────────────┘
```

One turn:

1. Maybe compact context (mask old tool output → summarise with small model).
2. Build request via the active **protocol**; stream the response. Stream
   monitors can abort generation (reasoning budget, degenerate repetition).
3. Parse into `ToolCall`s or a final answer; log the turn (tokens, timings,
   reasoning, raw response).
4. Run detectors (malformed / loop / overrun / token cap); tag failures;
   possibly nudge or abort.
5. For each call: checkpoint if mutating → execute via executor → post-tool
   filesystem check → log → append result message.

## Key design decisions

### Tool-call protocols (goal 2, and goal 1)

A `Protocol` turns the tool registry + history into request fields and turns a
response back into tool calls. Three implementations, selectable per config so
they can be A/B tested:

| protocol      | request                                               | constraint                                              | prompt overhead |
|---------------|-------------------------------------------------------|---------------------------------------------------------|-----------------|
| `native`      | OpenAI `tools` (needs `llama-server --jinja`)          | llama-server's lazy tool-call grammar (full grammar with `tool_choice=required`) | chat template's tool preamble + JSON schemas |
| `json_schema` | `response_format: {type: json_schema}` action envelope | llama-server converts schema → GBNF                     | one line per tool (signatures only) |
| `grammar`     | `grammar`: GBNF generated by argus                     | our GBNF: no free whitespace, fixed key order, optional `<think>` prefix | one line per tool |

The action envelope for the two constrained protocols is
`{"tool": "<name>", "args": {...}}` (plus an optional leading `"thought"`),
with `anyOf` over tools so `args` is validated per tool; `done` is a pseudo-tool
carrying the final summary. Because the sampler enforces argument structure,
the prompt only needs one-line signatures instead of full JSON schemas —
that is the main token saving. Our own GBNF also forbids insignificant
whitespace, which saves generated tokens on every call.

All protocols validate parsed arguments against the tool's JSON schema
harness-side (llama-server's lazy grammar is not applied in every case), so a
bad call becomes a `malformed_call` failure plus an error result the model can
recover from.

### Token overhead measurement (goal 1)

`argus overhead` renders the actual first request (system prompt + tools +
AGENTS.md + skill index) and measures it with llama-server's `/apply-template`
and `/tokenize` endpoints, differencing to attribute tokens to each part:
template baseline, system prompt, each tool schema, AGENTS.md, skills. When
the server is unreachable it falls back to an estimate and says so. The
overhead count is stored on every run so A/B reports show it.

### Streaming and stream monitors

The client streams SSE by default, assembling `reasoning_content`, `content`
and `tool_calls` deltas. Monitors see every delta and can abort the request;
closing the connection makes llama-server stop generating. Monitors:

- **reasoning budget** — abort after N reasoning tokens (runaway reasoning),
  then retry the turn once with thinking disabled and a nudge.
- **degenerate repetition** — abort when the tail of the output repeats.

Timings come from llama-server's `timings` object (prompt/gen ms, tokens/s,
cache hits) plus wall-clock TTFT measured client-side.

### Failure taxonomy (goal 3)

Stored in `failures(run_id, turn, tag, detail)`. A run can have several.

| tag              | detected when                                                                                   | harness response |
|------------------|-------------------------------------------------------------------------------------------------|------------------|
| `loop`           | same call (name + canonical args) repeated ≥ N times, or a short cycle (A,B,A,B…), or degenerate repetition in a generation | nudge once, abort if it continues |
| `overrun`        | generation continues past a final answer (role markers, repeated summary, `length` on a final answer); or activity after a declared completion; or (suite oracle) the task check already passed but the agent kept going | truncate / record |
| `malformed_call` | unparseable arguments, unknown tool, schema-invalid args, tool-call markup left in `content`, unparseable envelope | error result to model; abort after N consecutive |
| `token_cap`      | `finish_reason=length`, reasoning budget hit, context overflow, run token budget exhausted      | nudge / abort |

Additional non-core tags: `max_turns`, `timeout`, `server_error`,
`fs_violation`, `interrupted`.

### Executors (goal 4)

```python
class Executor:
    workdir: str
    def run(cmd, timeout, stdin=None) -> CmdResult   # bounded head+tail capture
    def read_bytes(path) -> bytes
    def write_bytes(path, data) -> None
    def list_files() -> list[str]                     # git ls-files | rg --files | find
```

`LocalExecutor` uses `subprocess` in its own process group (killed on
timeout). `SSHExecutor` wraps the same shell commands in
`ssh -o BatchMode=yes -o ControlMaster=auto … host 'cd WORKDIR && timeout …'`,
reusing a control socket so per-call latency stays low. Tools only ever talk
to an executor, so every tool behaves the same locally and in the VM. Tests
exercise the SSH path with a fake `ssh` shim that runs the command locally.

Output capture keeps a bounded head and a rolling tail, so `yes`-style
runaway output cannot exhaust memory, and smart truncation works on the
retained parts.

### Tools (goal 4)

- `read(path, offset?, limit?)` — `N<tab>line` numbering (the `cat -n` convention), line-length cap,
  binary detection, "showing a–b of N" footer.
- `edit(path, old, new, all?)` — exact match first, then a cascade of
  meaning-preserving normalisations (CRLF, copied line-number prefixes,
  trailing whitespace, uniform indentation shift with re-indent of `new`,
  unicode quotes/dashes), then similarity matching (applied only above a
  configurable threshold and only when the best candidate is unambiguous).
  Errors are specific: "matches 3 times at lines 10, 42, 97", or "no match;
  closest (91%) at lines 12–18:" plus a diff. On success returns a small
  numbered snippet around the change and a syntax warning for Python/JSON.
- `bash(cmd, timeout?)` — merged stdout/stderr, ANSI stripped, `\r` progress
  collapsed, repeated lines folded, head + tail kept, error-looking lines from
  the elided middle preserved.
- `glob(pattern)` — file listing from the executor, matched harness-side
  (`**`, braces; patterns without `/` match basenames at any depth).
- `grep(pattern, path?, glob?, ignore_case?)` — `rg` with a `grep -rn` fallback,
  capped matches and line length.

### Checkpoints and filesystem checks (goal 5)

A **shadow git repository** (separate `--git-dir`, `--work-tree=WORKDIR`,
its own index) snapshots the workspace without touching the user's repo,
index, branches or HEAD, and works in non-git directories. Honors
`.gitignore`; adds default excludes (`node_modules`, `.venv`, …).

- Before each mutating call (`edit`, `bash`): `git add -A && git write-tree`,
  commit onto `refs/argus/<run_id>` if the tree changed. Logged in
  `checkpoints`.
- After the call: snapshot again and `diff-tree` to get the exact change set.
  - `edit`: change set must be exactly `{path}` and the file must contain `new`
    → otherwise `fs_violation`.
  - `bash`: changed files are appended to the result (`[files changed: M a.py]`)
    and marked stale in the read tracker.
  - read-only tools never snapshot.
- `argus diff RUN` and `argus restore RUN [--to N]` use the refs.

### AGENTS.md and skills (goal 6)

- `AGENTS.md`: global (`~/.config/argus/AGENTS.md`) + workspace root, appended
  to the system prompt; its token cost is part of the overhead report.
- Skills: `*/SKILL.md` with YAML front matter (`name`, `description`) found in
  configured dirs (default `.agents/skills`, `.claude/skills`, plus a global
  dir). Only `name: description` lines go in the prompt. A `skill` tool is
  registered **only if skills exist** (zero overhead otherwise); its `name`
  parameter is an `enum`, so under constrained decoding the model cannot invent
  a skill. Invocations (via the tool, or by `read`ing a `SKILL.md`) are logged
  to `skill_invocations`.

### Compaction (goal 7)

Triggered when the projected prompt exceeds `threshold × n_ctx` (n_ctx from
`/props` or config):

1. **Observation masking** — replace tool outputs older than the last K turns
   with a one-line stub. Cheap; done in one batch so the KV-cache prefix is
   invalidated rarely.
2. **Summarisation** — if still over, send the middle of the history to the
   small model (separate base URL) and replace it with a summary message.
   Tool-call/result pairs are never split.

Every compaction is logged with tokens before/after, duration and the summary.

### Logging (goal 3)

SQLite (WAL), committed every turn so crashes leave a readable partial log.
Schema versioned with `PRAGMA user_version`.

```
batches(id, kind, name, meta_json, created_at)
runs(id, batch_id, variant, task_id, task, config_json, config_hash, workspace,
     executor, protocol, model, status, final_answer, n_turns, prompt_tokens,
     completion_tokens, reasoning_tokens, overhead_tokens, wall_ms,
     check_passed, check_output, error, started_at, ended_at)
turns(run_id, idx, prompt_tokens, completion_tokens, cached_tokens,
      reasoning_tokens, reasoning, content, finish_reason, aborted,
      ttft_ms, prompt_ms, gen_ms, total_ms, gen_tps, context_ids, raw_response)
messages(run_id, idx, turn_idx, role, content, tool_calls_json, tool_call_id, kind)
tool_calls(run_id, turn_idx, idx, call_id, name, args_json, ok, error, result,
           output_chars, truncated, duration_ms, fs_changes_json, checkpoint)
failures(run_id, turn_idx, tag, detail, created_at)
checkpoints(run_id, turn_idx, commit_sha, tree_sha, created_at)
skill_invocations(run_id, turn_idx, skill, path, via)
compactions(run_id, turn_idx, stage, tokens_before, tokens_after, ms, summary)
events(run_id, turn_idx, kind, data_json, created_at)
```

`messages` is append-only and `turns.context_ids` lists the message ids sent
in that request, so the exact prompt of every turn is reconstructable without
storing O(n²) copies.

### Mock server

`argus.mock.MockServer` is a stdlib `ThreadingHTTPServer` implementing
`/v1/chat/completions` (streaming and not), `/tokenize`, `/apply-template`,
`/props`, `/health`, `/v1/models`. It replays a **script**: a list of steps
(or a Python callable for dynamic tests). A step describes *what the model
does*, and the mock renders it for whichever protocol the request uses:
native `tool_calls`, a JSON envelope under `response_format`, or the same
under `grammar` — so one scenario can test all three protocols. It validates
its own constrained output against the request's schema/grammar, so schema
bugs surface in tests.

Step features: reasoning, content, tool calls (dicts or raw malformed
strings), raw content (e.g. unparsed `<tool_call>` markup), repeats (loops),
runaway reasoning/content that obeys `max_tokens` and emits
`finish_reason=length`, HTTP errors including llama-server's
`exceed_context_size_error`, per-chunk delays, and request assertions. Every
request is recorded for inspection. `argus mock-server --script s.json` runs it
standalone.

## Module layout

As built (differences from the original proposal: the GBNF generator got its
own module, the SSH executor lives in `ssh.py`, AGENTS.md loading and the
`skill` tool live in `skills.py`, and terminal output moved to `console.py`).

```
argus/
  cli.py          argparse entry point (argus …)
  config.py       dataclass config, TOML loading, -o key=value overrides, hashing
  agent.py        the tool loop: turns, retries, detectors, checkpoints, compaction hooks
  console.py      live progress reporter and `argus show` transcripts
  llm.py          OpenAI-compatible client: SSE assembly, stream monitors, errors
  protocols.py    native / json_schema / grammar, argument validation, markup salvage
  schema.py       JSON-schema subset validator and lenient coercion
  gbnf.py         JSON schema → GBNF (compact, fixed key order, <think> prefix)
  tokens.py       token counting (server /tokenize, fallback) and overhead report
  prompt.py       system prompt assembly
  skills.py       AGENTS.md loading, SKILL.md discovery, the skill tool
  detect.py       loop / overrun detectors and stream monitors
  compact.py      masking, small-model summarisation, drop fallback
  fsstate.py      shadow git snapshots, checkpoints, diff, restore, fs checks
  store.py        SQLite schema, writer, queries
  executors.py    Executor interface, LocalExecutor, bounded output capture
  ssh.py          SSHExecutor
  suite.py        task suites: load, workspace prep, checks, oracle, runner
  report.py       batch / A-B reports and statistics
  tools/
    base.py       Tool, ToolResult, ToolContext, FileTracker
    read.py  edit.py  fuzzy.py  bash.py  truncate.py  search.py (glob, grep)
  mock/
    server.py     mock OpenAI-compatible server
    script.py     steps, helpers, request expectations
    constraints.py  checks constrained output against the request
    gbnf.py       GBNF recogniser used by the mock and the tests
tests/            pytest, all against MockServer; no network
examples/         argus.toml, grammar.toml, suite/, skills/, mock/
```

## Config

TOML, all keys optional, unknown keys rejected (typos fail loudly). Any key can
be overridden on the command line: `-o agent.protocol='"grammar"'`. The full
annotated list is [examples/argus.toml](../examples/argus.toml).

```toml
[model]      base_url, model, sampling (temperature, top_p, top_k, min_p, …), max_tokens,
             context_window, stream, enable_thinking, timeout, retries, extra_body
[agent]      protocol, max_turns, max_wall_seconds, token_budget, max_reasoning_tokens,
             system_prompt, json_thought, grammar_think, loop_repeat, loop_abort,
             max_malformed, repetition_window, overrun_turns, reasoning_retry
[tools]      enabled, descriptions, read_*, require_read_before_edit, fuzzy_threshold,
             bash_timeout, bash_max_chars, bash_head_lines, bash_tail_lines, …
[executor]   kind = local|ssh, workdir, host, ssh_command, ssh_options, control_persist
[checkpoint] enabled, shadow_root, excludes
[context]    agents_md, global_dir, skills, skill_dirs
[compaction] enabled, threshold, keep_last_turns, mask, summarize, base_url, model
[log]        db, measure_overhead
```

## Things to verify against a real llama-server

The mock encodes my understanding of llama-server; these are the places most
likely to differ and are isolated behind small functions:

- whether `response_format`/`grammar` constrain the `<think>` block of Qwen3
  thinking models (the `json_schema` protocol disables thinking by default;
  the `grammar` protocol can allow a `<think>…</think>` prefix);
- the exact shape of streamed `tool_calls` deltas and of `timings`/`usage` in
  the final chunk;
- `/apply-template` accepting `tools` (used for exact overhead numbers).
